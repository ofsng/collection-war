# Data Architecture

> Audience: anyone designing a table, writing a migration or a query. Date: 2026-07-28.

---

## PostgreSQL is the source of truth

Everything durable lives in one PostgreSQL database. Nothing a player owns lives anywhere
else.

**Redis is not a database.** It holds cache entries, rate-limit counters and queued jobs. A
Redis restart must be an availability event, never a data-loss event. If losing Redis would
lose something a player owns, that thing is in the wrong place.

Chosen for the reason that matters most here: **transactions across every table**. A
marketplace purchase moves currency and ownership atomically because both are rows in the
same database. Split them and that guarantee is gone. See
[ADR-0009](../adr/ADR-0009-postgresql-source-of-truth.md).

## Transactions

Any operation touching more than one row runs inside a `UnitOfWork`.

### Isolation levels

`READ COMMITTED` is the default and is fine for most reads and simple writes.

**`SERIALIZABLE` is required** where an invariant spans rows the statements do not lock —
for example "this player's total escrowed gold must not exceed their balance", which
`READ COMMITTED` will violate under concurrency.

The list is data, not folklore, in `packages/domain/src/unit-of-work.ts`:

```text
marketplace.purchase · marketplace.createListing · marketplace.cancelListing
economy.transfer · economy.spend · inventory.consume · crafting.craft · rewards.claim
```

`SERIALIZABLE` costs serialization failures (SQLSTATE `40001`). Those are **expected and
normal**, not errors — the correct response is to retry, which `createUnitOfWork` does with
jittered backoff. Surfacing one to a player as a failure would make legitimate concurrent
play look broken.

### The rule about side effects

Work inside a transaction must perform **no external side effect**. No HTTP call, no email,
no push notification.

A rolled-back transaction cannot un-send an email. Side effects are enqueued to the outbox
inside the transaction and performed after it commits.

## Optimistic concurrency

Mutable player-owned rows carry a `version`. A write includes the version it read; the
database rejects it if the row moved underneath.

```sql
UPDATE owned_creatures SET level = $1, version = version + 1
WHERE id = $2 AND version = $3;
-- 0 rows affected → someone else wrote first → STALE_WRITE, re-read and retry
```

Preferred over pessimistic locking because it does not hold a lock across a network round
trip — and because a lost update in this system means a player's progress silently
disappears.

## Identifier strategy

**UUIDv7, everywhere.**

- The server can mint an id before the row exists — which the outbox and idempotency keys
  both rely on.
- It is time-ordered, so it indexes well as a primary key. UUIDv4 scatters B-tree inserts
  and degrades write performance as the table grows.
- It leaks nothing. A sequential id tells a competitor exactly how many players signed up,
  and lets a client enumerate other players' resources.

Ids are opaque to clients. A client must never parse, derive or predict one.

## Timestamps

Every timestamp is `timestamptz`, generated by the **server**, stored in UTC.

A client never supplies a timestamp for anything that matters. A device clock is
attacker-controlled input, and "my expedition finished early" is a trivially exploitable
consequence.

The local PostgreSQL container is initialised with `--locale=C` so ordering is deterministic
and does not depend on the host locale — which matters, since Turkish casing rules differ
from C and the bootstrap machine runs `tr_TR`.

## Immutability and history

| Data              | Mutability                       | Why                                                  |
| ----------------- | -------------------------------- | ---------------------------------------------------- |
| Ledger entries    | **Immutable, append-only**       | Financial history that can be edited is not an audit |
| Audit records     | **Immutable**                    | Same                                                 |
| Battle results    | **Immutable**                    | Replayable from seed + content version               |
| Outbox rows       | Append, then status updates only | Delivery bookkeeping                                 |
| Player profile    | Mutable + versioned              | Ordinary state                                       |
| Owned creatures   | Mutable + versioned              | Ordinary state                                       |
| Catalogue content | **Immutable per version**        | Old outcomes must replay under old data              |

A mistake in immutable data is corrected by a **compensating record**, never by an edit.

## Soft deletion

Player-owned records carry `deleted_at` and are never hard-deleted by ordinary application
paths.

- an accidental delete is recoverable;
- a dispute months later is investigable;
- a marketplace listing referencing a deleted creature does not become a dangling reference.

Genuine erasure — a data-protection request — is a separate, deliberate, audited process
with its own runbook. It is not something an ordinary code path can reach for.

Every query against a soft-deletable table filters `deleted_at IS NULL`. A partial index
keeps that cheap:

```sql
CREATE INDEX ... ON owned_creatures (player_id) WHERE deleted_at IS NULL;
```

---

## Indexing principles

1. **Index for the queries you actually run.** Every index costs write throughput and disk.
2. **Composite column order follows the query:** equality columns first, then range, then
   sort.
3. **Partial indexes for filtered queries** — the soft-delete case above.
4. **Unique constraints are correctness, not performance.** The idempotency-key uniqueness
   index is the mechanism that prevents double spending; it is not an optimisation.
5. **Foreign keys get indexes.** PostgreSQL does not create them automatically, and a
   missing one makes cascading deletes and joins scan.
6. **Measure before adding.** `EXPLAIN (ANALYZE, BUFFERS)` on real data volumes.

## Content versioning

Game content — species stats, drop tables, quest definitions, balance numbers — is
versioned. Every outcome computed from it records the version.

Two problems this solves, both of which are unfixable retroactively:

1. **Auditability.** A battle fought in March must replay under March's rules. Without a
   recorded version, replay silently applies today's numbers and produces a different answer
   than the player saw.
2. **Client skew.** A released mobile build may hold stale content. The server decides
   regardless, but it needs to know what the client believed in order to explain a mismatch.

`ContentVersion` and `BattleEngineVersion` are separate: rules and numbers change
independently.

Generated from the Drizzle schema, reviewed as SQL, committed, applied in order.

`drizzle-kit push` is deliberately not wired to any script. It diffs a live database against
the schema and applies the difference with no migration file — so the change is neither

## Backups

Not yet configured — there is no hosted database to back up. The requirements, recorded now
so they are not invented during an incident:

- automated daily full backups with point-in-time recovery;
- **restore tested on a schedule**, because an untested backup is a hypothesis;
- retention long enough to cover a slow-burning economy bug (30 days minimum);
- encrypted at rest, with the key stored separately from the backup.

See [backups runbook](../runbooks/BACKUPS.md).

## Retention

| Data             | Retention                       | Reason                                                                |
| ---------------- | ------------------------------- | --------------------------------------------------------------------- |
| Player account   | While active + a defined window | Recovery, then erasure                                                |
| Ledger entries   | **Indefinite**                  | Financial records; a shortened window makes reconciliation impossible |
| Audit records    | Long (years)                    | Dispute and compliance                                                |
| Battle results   | Medium                          | Replay and support                                                    |
| Analytics events | Medium, pseudonymous            | Product analysis                                                      |
| Application logs | Short (weeks)                   | Debugging; also the highest personal-data risk                        |
| Outbox rows      | Days after publication          | Bookkeeping only                                                      |
| Idempotency keys | A bounded window                | Long enough to cover a late retry; not forever                        |

## The current schema

Two tables, both platform infrastructure:

**`outbox`** — transactional event delivery. Created before any domain table because
retrofitting reliable event delivery onto a system that already fires side effects inline is
a rewrite, not a refactor.

**`idempotency_keys`** — a unique index on `(key, scope)`. That index _is_ the double-spend
protection; the rest of the table is bookkeeping.

**There is no game schema.** Designing tables before the domain specifications are approved
would lock in decisions that become expensive once real player data exists. The planned
entity map is in the [domain map](../domains/DOMAIN_MAP.md); the design process is
[CW-0002](../tasks/BACKLOG.md).
