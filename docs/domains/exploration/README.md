# Domain: Exploration

> **Tier 3 — Supporting.** Status: **PROPOSED, not implemented.** Date: 2026-07-28.

## 1. Purpose

Timed expeditions: a player sends creatures away for a period and receives materials when the
time elapses.

## 2. Responsibilities

- Expedition definitions: duration, requirements, reward tables.
- Starting an expedition and reserving the creatures.
- Completing it when server time says it is due.
- Rolling rewards from a seeded generator and granting them.

## 3. Owned data

| Table                    | Holds                                                                                          |
| ------------------------ | ---------------------------------------------------------------------------------------------- |
| `expedition_definitions` | Versioned: duration, requirements, reward table                                                |
| `expeditions`            | `player_id`, definition, creature ids, `started_at`, `completes_at`, status, **seed**, claimed |

`completes_at` is computed and stored by the **server**. `seed` is stored so the reward roll
is reproducible and a "that drop looks suspicious" question is answerable.

## 4. Public interface

```text
listExpeditions(playerId) → Result<ExpeditionView[]>
start(playerId, definitionId, creatureIds, idempotencyKey) → Result<ExpeditionId>
getActive(playerId) → Result<Expedition[]>
claim(playerId, expeditionId, idempotencyKey) → Result<ExpeditionRewards>
cancel(playerId, expeditionId) → Result<void>
```

## 5. Incoming dependencies

`quests` (exploration objectives) · `habitats` (shared time mechanics)

## 6. Outgoing dependencies

`owned-creatures` (reserve and release) · `inventory` (material rewards) ·
`economy` (currency rewards) · `progression` (experience)

## 7. Domain events

`Exploration.ExpeditionStarted` · `Exploration.ExpeditionCompleted` ·
`Exploration.RewardsClaimed`

## 8. Security concerns

**Time is the attack surface here**, and it is the clearest illustration of why client time
is never trusted.

- **Completion is decided by server time.** A device clock is attacker-controlled input; a
  client-reported "it's finished" is a free instant expedition.
- **Reward rolls happen server-side**, from a stored seed. A client that could roll would roll
  until it liked the result.
- **Creatures are reserved**, and a reserved creature cannot battle, be listed or be consumed.
  Otherwise one creature could be on three expeditions and in a battle simultaneously.
- **Claim is idempotent.** A retried claim must not grant rewards twice — the most likely
  duplication bug in the domain.
- **Cancellation** must release the creatures and grant nothing, transactionally.

## 9. Economy concerns

Exploration is the **primary passive material faucet** — value generated by waiting rather
than by playing.

That makes it the easiest faucet to over-tune: it scales with the number of accounts, not with
engagement, so it is also the mechanic most attractive to multi-account farming. Reward
tables here need economy review, not content review.

## 10. Expected scaling pressure

The completion sweep. A naive "scan every expedition every minute" degrades linearly as the
table grows.

Response: index on `completes_at` with a partial index for active rows; process in batches;
and prefer scheduling a job per expedition over sweeping the whole table.

## 11. What this domain must never do

- Never accept a client-supplied completion time, or trust a client's claim that time passed.
- Never roll rewards on the client.
- Never grant rewards without an idempotency key.
- Never allow a reserved creature to be used elsewhere.
- Never complete an expedition before `completes_at` — including for administrative
  convenience, which is how a "helpful" support action becomes an exploit.
